# Daily Driver Memory Scenario v1

This fixture is an executable product specification for a transparent personal-memory system. It follows
one fictional user, Maya Chen, across assistant chats, project meetings, and tool observations from
2026-09-01 through 2026-09-18.

Maya's name is configured profile identity, not inferred from speaker labels. All of her chat and meeting
turns are labeled `User` and carry the structural user role; the runner maps that role directly to the
singleton `you` entity. `Maya Chen` remains a visible alias on You and lets separately sourced references,
such as an issue-tracker assignee, resolve to the same identity.

The benchmark is primarily about memory artifacts and lifecycle behavior. Question answering is a secondary
test of whether those artifacts remain useful during retrieval.

## Scenario

Maya is building a local meeting-memory application. Early conversations refer only to "the meeting idea";
several episodes must accumulate before **Project Lantern** deserves a page. Once that page is mature, later
facts should attach to it without creating overlapping pages. Maya also coordinates with Priya Raman and
Luis Ortega, evaluates local transcription tools, schedules a pilot, and keeps a separate family oral-history
project that the memory system must discover from recurring activity rather than an explicit project name.

The sources deliberately include:

- assistant proposals that Maya does and does not accept;
- repeated evidence that should strengthen one rendered fact rather than add bullets;
- relative dates anchored to each episode's occurrence time;
- tool results that inform a project and unrelated search noise that should remain source history;
- an explicitly changed deadline;
- a meeting imported from the wrong workspace and later retracted;
- incidental objects, restaurants, documents, and routine meetings that must not become pages.

## Files

- `scenario.yaml`: ordered source episodes, stable source/segment IDs, lifecycle actions, and source-level
  retention expectations.
- `gold_claims.yaml`: expected atomic claims with semantics, exact provenance, lifecycle state, and the
  consolidated fact each claim supports.
- `gold_checkpoints.yaml`: expected short-term queue, entities, placements, and reconciliation state after
  each Dream/review/retraction checkpoint.
- `gold_wiki.yaml`: authoritative structured final wiki. It defines which consolidated facts appear on each
  page and in which section.
- `wiki/*.md`: ideal human-readable rendering. Wording is illustrative; `gold_wiki.yaml` is authoritative.
- `probes.yaml`: semantic retrieval and answer probes with required facts, forbidden facts, and evidence.
- `rubric.yaml`: dimensions, severity, and the intended interpretation of results.

## Authority and non-goals

Stable fact IDs, entity IDs, placements, states, and provenance are normative. Exact LLM wording, claim IDs
generated by a system under test, Markdown punctuation, and page ordering within a section are not.

The fixture does not require every durable claim to become a separate wiki bullet. Several source-grounded
claims may support one consolidated fact. A fact may also change presentation over time: an old deadline can
remain in a project timeline while only the replacement appears under current next steps.

Ordinary facts render once on their canonical owner's page. A `project_role` relationship remains one
person-owned fact but deliberately renders on both the Person/You and Project endpoints with the same fact ID
and provenance. This makes both “What does this person do?” and “Who works on this project?” natural wiki
navigation paths without duplicating canonical memory.

## Checkpoint summary

1. `cp1_pre_dream`: new claims are available in short-term memory; no Lantern page exists.
2. `cp2_first_dream`: sparse profile pages exist, but the unnamed meeting effort remains deferred.
3. `cp3_second_dream`: cross-episode evidence establishes Project Lantern and a mature Priya page.
4. `cp4_mature_update`: local-only architecture, pilot plans, and the inferred Family Oral History project are incorporated.
5. `cp5_pending_change`: the pilot-date correction is awaiting review and neither date is authoritative.
6. `cp6_change_applied`: September 28 is current; September 22 is retained only as superseded history.
7. `cp6_wrong_import`: the imported source is visibly present before retraction.
8. `cp7_retraction_applied`: the wrong-workspace merger claims and event page are removed.
9. `cp8_final`: later evidence consolidates without wiki fragmentation or duplicated facts.

Run the fixture validator with:

```bash
uv run python -m benchmarks.mycelium_bench.daily_driver \
  validate benchmarks/fixtures/daily_driver_v1
```

Run the scenario through the configured production pipeline with:

```bash
uv run python -m benchmarks.mycelium_bench.daily_driver \
  run benchmarks/fixtures/daily_driver_v1 \
  --output-dir benchmark_runs/daily-driver-v1-run \
  --config-path mycelium.toml
```

The run directory contains the complete Mycelium store, a snapshot and generated
Markdown wiki for every checkpoint, `comparison.json` with layer-specific diagnostics,
and a concise `REPORT.md`. The runner never simulates unsupported lifecycle operations;
for example, source retraction is recorded as a capability gap until Mycelium implements
it. Recompute the deterministic comparison after changing comparison logic without
calling the LLM again:

```bash
uv run python -m benchmarks.mycelium_bench.daily_driver \
  compare benchmarks/fixtures/daily_driver_v1 \
  --output-dir benchmark_runs/daily-driver-v1-run \
  --config-path mycelium.toml
```
